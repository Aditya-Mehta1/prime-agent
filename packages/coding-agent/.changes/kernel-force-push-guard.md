- Added a force-push guard to the kernel bash tool: `git push` invocations carrying a force flag (`--force`, `-f`, bundled short options, a `+`-prefixed refspec) are refused before execution when their target names main/master or `@{u}`-style refs, when `--all`/`--mirror` would rewrite every branch, or when the refspec is implicit and the probed upstream (`git rev-parse @{u}`, run only on a pattern match in the command's replayed cwd) exists; `--force-with-lease` and `--force-if-includes` are never refused, plain pushes pay nothing, and force-pushes the guard cannot check statically (globs, substitutions, xargs-fed refspecs, eval or quoted `sh -c` payloads, unreplayable `cd`/`git -C`/GIT_DIR relocations) are refused outright. Explicit bypasses: `bash(command, allow_force_push=True)` or `PI_BASH_ALLOW_FORCE_PUSH=1`, where the env bypass is frozen at kernel start so mid-session `os.environ` writes cannot neuter the guard (they are ignored and warned about loudly).
- Hardened the kernel force-push guard against every bypass class found in review: the scan reads the command the way the shell does (backslash-newline continuations joined, quoted escapes folded, ANSI-C `$'...'`/`$"..."` bodies decoded, inline `-c alias.X=...` bodies expanded, `GIT`/`Git.exe`/`/usr/bin/GIT`/`SH` casing) and refuses anything it cannot resolve statically: a push argument holding a variable, glob, or substitution (`f=-f; git push $f ...` or `$BRANCH`), a URL or scp-style remote (whose implicit refspec is not a refspec), `env -C` / `env --chdir` / `env -S` wrappers, a git subcommand that is not a builtin (a repository or user alias, or an external `git-` program), an implicit refspec on a branch with no upstream (the target then comes from push.default, remote.<name>.push, or remote.<name>.mirror), and a command that ends in a line continuation. The allowed set is unchanged: a literal `--force-with-lease` or `--force-if-includes`, `--dry-run`, force to a non-protected branch, plain pushes, and both documented bypasses all keep working - but an argument the scan cannot resolve is refused even alongside `--force-with-lease`, because the shell can expand it into `-f`, and `-f` skips the lease compare-and-swap (a bare `--force-with-lease` over a stale remote-tracking ref is rejected as `stale info`, while `--force-with-lease -f` and `--force-with-lease origin +main` rewrite the ref).
- Refused the nested-payload, detached-HEAD, alias-shadowing, and command-table gaps found in the second review round of that guard: a payload inside a payload (`env -S 'sh -c "git push -f origin main"'`, `eval 'sh -c "git push -f origin main"'`, `sh -c "eval 'git push -f origin main'"`) is now re-scanned by every payload scanner with a depth cap; an implicit force push from a detached HEAD is refused (`push.default=matching`/`current` and `remote.<name>.mirror` ignore HEAD and still push main); an inline alias named after one of git's own commands is no longer expanded (git runs the command, not the alias), and that command table is calibrated to the oldest git verified here (Apple git 2.50.1) so a command only a newer git knows is refused rather than trusted; an alias chain that stops changing is no longer reported as unresolvable; and the refusal for a git subcommand the guard cannot resolve now points at the real subcommand first.
- Closed the whole "argv the guard cannot resolve" family in one rule: a force-push pattern next to a command word the guard cannot resolve (a variable, substitution, backtick or `${IFS}` expansion, an unquoted `{a,b}`/`{a..b}` brace expansion, or an unmodeled wrapper such as `ssh`, `chroot`, `timeout`, `parallel`, `docker`, `sudo`, or `xargs`) is refused, as is a force-push pattern reaching a shell through a pipe, here-string, input redirect, or `xargs` (`echo '...' | sh`, `bash <<< '...'`, `sh < payload.sh`), and a payload whose text holds an expansion (`cmd='git push -f origin main'; sh -c "$cmd"`). Scoping is unchanged for commands without a force-push pattern: `X=1; git push origin feature`, `echo $HOME && git push origin feature`, `ls $(pwd)`, `X=$(date); echo $X`, `echo "$(git rev-parse HEAD)" | cut -c1-7`, and an echo of a force-push string with no interpreter stay allowed.
- Refined that family rule to skip an env-assignment prefix when it decides whether the command word is dynamic: `X=$Y git push -f origin feature` and `GIT_TRACE=$DEBUG git push -f origin feature` run again (the visible git word decides, and the relocation, force, and target rules still apply to it). A command word genuinely built from a substitution (`$(which git) push -f origin main`, `$(printf git) push -f origin main`) and an unquoted brace expansion (`{git,-c} user.email=x push -f origin main`) stay in the declared fail-closed set.
- Closed four spellings of the unresolvable-argv family that the Family-close review parked, each of which really force-updated a protected `main` through kernel `bash()` before this round: a path-qualified or relative shell now counts as the interpreter on a conduit (`printf '%s\n' 'git push -f origin main' | /bin/sh`, `| /bin/bash`, `| ./sh`), while a script whose name merely ends in a shell name (`payload.sh`) stays data; a command word whose expansion is written inside double quotes is dynamic like an unquoted one (`c=git; "$c" push -f origin main`, `"$(printf git)" push -f origin main`), because the shell expands `$` and backticks inside double quotes (a single-quoted `'$c'` stays inert, and only the dynamic-word test reads that view); the command-word walk steps over a wrapper the guard models (`env`, `command`, `builtin`) and over its option words and their separate values (`env -i $c push -f origin main`, `env -u FOO $c push -f origin main`, `command -p $c push -f origin main`) instead of reading the wrapper itself as the command word; and the family scan slices the text the word scan actually read, so a folded line continuation or escape no longer shifts every word span out from under the wrapper check (`echo a\<newline>;ssh build-box "git push -f origin main"`, and the quoted wrapper `"ssh" build-box "git push -f origin main"` reads as its folded word value). Declared residuals of the same shape, unchanged and out of scope for a pre-spawn text guard: a shell alias the shell expands at run time (`shopt -s expand_aliases` and `alias git='git push -f origin main'` are inert while the alias is only defined or invoked in the same command, because the kernel runs the whole command as one `bash -c` parse unit, while `eval git` re-parses its argument and really rewrites `main`) is not modeled -- the fix shape is a shared shell-invocation analyzer for the alias, `eval`, and startup classes across the sibling kernel guards, which the rm guard already carries for its own vectors, not a local rule; and the scan budget and substitution cap are process-global, so two threads calling `bash()` at once can replace each other's budget for the duration of a scan -- a robustness bound rather than a bypass, because every rule still runs and the worst case is an over-refusal or an unbounded scan, with a per-invocation budget (contextvars or an explicit scanner parameter) as its fix shape.
- Closed the six threads the second review pass parked: a push whose own command writes a `remote.<name>.mirror` or `remote.<name>.push` key (`git -c remote.origin.mirror=true push origin`, `git config remote.origin.mirror true && git push origin`) is refused before it can turn a plain push into a forced one, word-scanned so both the inline `-c` and the same-text `git config` chain match (the state route, a key written in an earlier command and read by a later plain push, still needs an upstream-probe consult before an implicit push is allowed and stays the owner's call); the inline-payload rule now governs `fish` and the csh family in every spelling fish accepts (`-c`, glued `-c'...'`, `--command`, `--init-command`, `-C`, all verified against fish 4.9) plus their piped-stdin conduits, while their script files stay the declared residual; a `GIT_DIR`/`GIT_WORK_TREE` export anywhere in the command prefix, including one the prefix's tail separator hides, relocates the repository like a `cd` and is refused the same way; quoted parens are data again in the cwd replay, so `echo "("; cd repo && echo ")"; git push -f origin HEAD` no longer drops the cd as a subshell frame and the push is judged where it really runs; `PRIME_AGENT_BASH_COMMAND_PREFIX` is read once and the same text feeds both the scan and the spawn, so a concurrent in-process env flip can no longer land a scanned-benign/spawned-force push; and the wrapper walk steps over `env`'s value options the way getopt parses them (bundled value-taking letters like `env -vu NAME`, and unlisted value options like `-P`, `-a`, `--argv0`), so the expansion after them is recorded as the command word instead of the option's operand.
- Closed the four open spellings the third review pass parked, each one verified as a real force-update of a protected `main` through kernel `bash()` before the fix: `-C` is a payload letter for fish only, because the POSIX shells and the csh family treat it as a valueless flag (noclobber) and reading it as a payload handed the `-c` that followed to it as its operand, dropping the real payload from the scan (`bash -C -c 'git push -f origin main'`, `bash -Cc '...'`, and the same with `sh`, `dash`, `ksh`, `zsh`); fish keeps walking after a payload instead of stopping at the first one, since it runs every payload it is given (`fish -C 'echo done' -c 'git push -f origin main'`); the `remote.<name>.mirror`/`remote.<name>.push` detector is case-folded now, because git reads the section and the variable name case-insensitively (`git -c remote.origin.MIRROR=true push origin`, `git -c REMOTE.origin.mirror=true push origin`, `git config Remote.origin.mirror true && git push origin`), and it reads the env spelling of the same write too (`GIT_CONFIG_COUNT=1` with `GIT_CONFIG_KEY_0`/`GIT_CONFIG_VALUE_0`, `GIT_CONFIG_PARAMETERS`, and an env key word the guard cannot read such as `GIT_CONFIG_KEY_0=$K`). A literal `$` in a quoted refspec (`git push -f origin 'feature$release'`) is still refused by the declared unresolvable-argument rule, which treats every argument the scan cannot resolve as a possible force flag; the env table's `-P` entry is BSD env's real value option (`-P utilpath`), since neither BSD env nor GNU env 9.11 has a `--path`.
